# Post Hooks

A hook is the first line a reader sees. It earns attention with specificity,
not volume. These are structural patterns written for this skill; they contain
no copied posts. Fill the brackets from the claim ledger only.

## The thread is 2–3 hooks, not an explainer

- **Post 1 — the strongest hook.** The most surprising verified fact, number, or
  contradiction. No link. Do not resolve it.
- **Post 2 — the second hook.** The mechanism, the cost, or the implication.
  Still a hook; it opens a new gap.
- **Post 3 — the last hook plus the link.** One more specific fact and the
  source URL. If the thread is 2 posts, the link goes in post 2.

If a sentence explains the whole result, cut it. The reader clicks the source to
get the rest. A 7-post explainer is not this skill.

## Shapes that work

| Shape | Pattern | Use when | Honesty guard |
|-------|---------|----------|---------------|
| Number first | "[N units] [outcome] with [constraint]." | One strong, verified number | The baseline appears in the same post |
| Contrast | "[Common belief]. [This result] says otherwise: [number]." | The source states the belief | Quote the belief from a source, not impression |
| Constraint | "[Result] using only [small resource]." | The efficiency or cost claim is the finding | State the resource figure with units |
| Plain question | "Why does [observed behavior] happen? A new paper answers it." | The source actually answers it | The post must point at the answer, not stall |
| Failure report | "I tried [method] on [task]. It broke at [condition]." | Your own replication or extension | Say what you ran and with what code |
| Scope check | "[Result] holds for [conditions]. Here is what is not shown." | A strong result with narrow scope | Take the scope from the methods section |
| Before and after | "[Old way: number] to [new way: number]." | Both numbers come from the same source and setup | Same hardware, dataset, and metric on both sides |
| Named mechanism | "[Source] calls it [name]. The rule: [one line]." | The source gives the idea a name | Use the source's own name and definition |

## Rules for the first post

- Lead with the concrete thing: a number, a mechanism, a condition, or a real
  question. A first line that could open any post is the wrong first line.
- One idea. The second hook goes in post 2, not the same post.
- Plain nouns and verbs over adjectives. If an adjective carries the claim
  ("dramatic", "huge"), replace it with the number.
- No link in the first post.
- Read it aloud as a skeptical expert in the field. If they would ask "compared
  to what?", add the baseline.

## Words that need evidence before they appear

State-of-the-art, first, only, best, outperforms, breakthrough, solves, proves,
beats, "game-changer". Each needs a ledger row that supports it (for example, a
results table showing the comparison) or it is cut. "Shows" and "proves" need
stronger evidence than "suggests" and "finds"; match the source's own verb.

## What travels, without overclaiming

- **Specificity.** A concrete number with its baseline is more shareable than an
  adjective. "18% vs 12%" travels; "much better" does not.
- **A true surprise.** The contrast is only a surprise if a cited source states
  the expectation. Otherwise it is a claim the reader cannot check.
- **A visual that carries the claim.** The source's own figure, screenshot, or
  GIF that shows the same number as the hook is what a reader screenshots.
- **Utility.** A builder's takeaway or a scope check gives the reader something
  to do or to avoid. Label it as inference when it is yours.
- **One hook per post.** A 2–3 post thread that opens a new gap per post is read
  to the end; a thread that resolves everything is not clicked.

These are structural patterns, not measured effects. The skill does not promise
virality, and it never trades accuracy for reach.

## Example shape (not a real source)

1. "The workflow Google's engineers use to stop AI from shipping sloppy code has
   one rule: no code until the plan survives."
2. "It splits the work into an Elephant that holds the whole project context and
   Goldfish reviewers that start with no memory, so they do not inherit the
   Elephant's blind spots."
3. "A Goldfish has to paraphrase the design back. If it cannot, the doc is
   ambiguous. Then hostile Goldfish attack it, and a final one checks
   implementation readiness. Repo: [link]"

Each post opens a gap. The link carries the rest.
